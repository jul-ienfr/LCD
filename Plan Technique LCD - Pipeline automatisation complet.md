## 1. Corrections structurantes v2 (issues trouvées pendant l'optimisation)

1. **KeyMaster + Nuki via Matter = codes impossibles.** L'intégration Matter de HA n'implémente pas `lock.set_usercode` : un Nuki appairé **uniquement** en Matter ne peut pas recevoir de PINs depuis HA. → Architecture retenue : **Nuki Go + Keypad 2.0** (Matter/Thread pour le verrouillage local <1 s) **+ Nuki Hub sur ESP32** (open source, ~8 €, Bluetooth→MQTT, topics `keypad/command/add|delete`) pour la gestion des codes + **KeyMaster** (HACS) comme générateur/planificateur/UI → automation : changement de slot KeyMaster → publish MQTT vers Nuki Hub. Fallback : saisie manuelle du code via app Nuki (Bluetooth sur place).
2. **Deux radios obligatoires** (1 radio = 1 protocole) : **SMLIGHT SLZB-06p7 PoE (CC2652P7, Z-Stack)** coordinateur Zigbee2MQTT + **Home Assistant Connect ZBT-2** en routeur de bordure Thread (add-on OpenThread Border Router) pour Nuki/Keypad. SLZB en PoE/Ethernet (jamais WiFi pour un coordinateur) placé central, loin du mini-PC.
3. **Clim** : pas de module constructeur (cloud) → **Broadlink RM4 mini** (~22 €) en IR 100% local via `python-broadlink`, apprentissage télécommande, bridage par automations.
4. **Vanne d'eau** : pas de plomberie en copro → **bras motorisé Aqara Valve Controller T1** (~65 €, se visse sur vanne quart-de-tour existante, réversible, sans plombier) plutôt qu'électrovanne à souder.
5. **LL/LV/TV** : suivi + alertes fin de cycle via **prises connectées Zigbee avec mesure (Nous A1Z ~12 €)** — nouveau poste ajouté (§5.9).
6. **Présence fusionnée** : calendrier + code serrure + **2 PIR Aqara (~13 €)** + conso électrique → extinction oublis (lumières/TV/clim), Eco chauffage, preuve d'occupation.

## 1.5 Architecture multi-logements : feature-flags + 1 HA/site + central mutualisé (validé 2026-10-05)

**Principe** : chaque option du plan est activable/désactivable par logement. Ex : log1 = Nuki Go + Keypad, log2 = pas de serrure (boîte à clés). Tout s'adapte automatiquement (automations, dashboards, supervision, decision-engine) sans dupliquer de code.

### 1.5.2 Automations adaptatives (même trigger, 2 branches)

Exemple accès (cas log1/log2) — trigger identique : résa confirmée (webhook moteur direct §4-bis / poll ICS) pour `{{ logement_id }}` :
- **si `enable_smart_lock == on`** (log1) : KeyMaster PIN 6 chiffres slot 1-10 → publish MQTT `nukihub/log1/keypad/command/add` → envoi auto (message moteur direct + SMS/Telegram, langue voyageur socle + auto §5.7-ter) J-2 + rappel J-1 → révocation départ+30 min + vérif `lock`.

Même pattern partout : `chauffage_fp off` → skip Versatile/pré-chauffe/bridage 21 °C ; `vanne_eau off` → fuite = alerte seule sans fermeture <2 s ; `bruit off` → pas d'escalade 3 niveaux ; `voix/tablette off` → SMS/Telegram + QR papier. `geoloc_voyageur off` (défaut) → aucune localisation, optimisations énergie/accès sur calendrier + PIR + code serrure seuls ; `on` (opt-in par séjour uniquement) → `device_tracker.logX_voyageur` + zones home/away pour pré-chauffe/ECS/clim + accueil porte. `etat_lieux_auto off` → état des lieux manuel ménage seul (photos Companion App ménage) ; `on` → parcours voyageur PWA entrée+sortie (photos obligatoires + vidéo optionnelle) + comparatif avant/après hôte/ménage + blocage clôture si manquantes. `traca_intervenants off` → checklist ménage déclarative seule (cases cochées, pas de preuve exigée) ; `on` → parcours intervenant PWA/QR obligatoire (pointage arrivée/départ via téléphone → durée présence + temps travail loggués, photos avant/après obligatoires par pièce + vidéo optionnelle → `/config/interventions/logX/<date>_<presta>/`, blocage clôture/facturation si manquantes, temps facturé = temps pointé). Decision-engine lit le même YAML et saute les branches désactivées. Contrat zéro-touch conservé.

**Branches nouveautés 2026-10-05** : `mode_gestion` → 1 select dashboard pilote pricing + seuils + dispatch + alignement (§3-bis) ; `menage_facturation` → affiche le facial TTC par canal avec ou sans ligne ménage séparée (§12.2-ter) ; `inventaire_biens off` → Grocy consommables seuls, pas de fiche bien ni stats usure ; `on` → scan QR/NFC → `custom/inventaire/logX/biens.yaml`, +1 utilisation par clôture ménage, alertes dormant/dégradé/garantie (§5.6-bis). `events_auto off` → K_events saisie manuelle ; `on` → `calendar.logX_events` (4 sources) → K_events auto affiché Vue Prix (§3-ter). `concurrence_suivi on` → todo trimestriel + proposition ±10 % 1-tap (§3-ter). `sinistre_auto off` → dossier manuel ; `on` → dossier auto + dispatch presta + suivi caution (§12.4-bis). `annuaire_presta off` → contacts libres ; `on` → `custom/prestataires/logX.yaml` + score prix×note×dispo×délai + comparatif (§12.4-bis).

Dashboards : cartes en `visibility: condition state input_boolean... == on`. Watchdog par logement : batterie serrure <25 %, LQI, capteur muet >24 h **seulement si feature on**.

### 1.5.2-bis Conformité copropriété par logement → règlement + contrat voyageur (validé 2026-10-05)

**Principe** : chaque logement a son bloc `copro:` dans `logements.yaml` (§1.5.1). Tant que `copro.verifiee: false`, la mise en ligne est **BLOQUÉE** (dashboard SYSTÈME rouge + `sensor.logX_config_ok: copro_non_verifiee` + rappel todo). Le wizard onboarding logN (§1.6.4) exige : photo règlement copro (articles occupation) + accord syndic écrit + heures calmes + animaux + occupants max → versés dans `docs/logN/copro/` (jamais commités si repo public : dossier privé client).

**Propagation automatique** (templates `docs/templates/reglement-interieur.{fr,en,es,it,de}.md` + toute autre langue maternelle en auto §5.7-ter + CGV moteur direct (§4-bis) + annonces) :
- `fetes_interdites: true` → clause injectée partout : « **Fêtes, soirées et rassemblements interdits** — occupation bourgeoise exigée par le règlement de copropriété ({{ articles_ref }}). Tout manquement = fin de séjour anticipée sans remboursement + retenue sur caution/état des lieux sur justificatifs. » + interdiction Airbnb fêtes (2022) rappelée + consigne bruit capteur 3 niveaux §5.9.
- `heures_calmes` → clause bruit : « Silence {{ heures_calmes }} dans tout l'immeuble (parties communes + logement fenêtres ouvertes), niveau sonore modéré le jour. » + affiché PWA Guide + QR chambre.
- `animaux` → clause animaux copro-alignée (jamais plus permissive que la copro ; animaux d'assistance toujours acceptés, loi).

### 4-ter. Plateformes d'intérêt : OTA + direct + vitrines gratuites + options payantes (validé 2026-10-05)

## 6. Voix IA locale — chaîne complète et choix définitifs (voix 100 % smartphone voyageur par défaut, validé 2026-10-05)

**Chaîne par défaut (`voix: true`, `voix_satellite: false`)** : **smartphone personnel du voyageur uniquement (BYOD strict — aucun téléphone propriétaire laissé dans le logement, jamais)** : Companion App Assist / WebRTC + PWA via QR d'accueil → **consentement explicite à chaque interaction** (bouton « Autoriser » par échange, révocable à tout moment, refus = réponse texte/guide QR) → STT téléphone → Assist pipelines (socle 5 langues + maternelle auto §5.7-ter, langue = `input_text.logX_langue_voyageur` depuis résa, défaut FR) → agent conversation **API LLM externe par défaut** (texte seul, jamais d'audio) + **fallback local Ollama si WAN down** (prompt système + base connaissances logement + **scripts sûrs exposés uniquement**) → réponse texte + TTS téléphone. Voix (STT/TTS) = 100 % côté smartphone voyageur ; en mode téléphone, seul le texte transcrit part en API (registre RGPD, aucun micro fixe ni téléphone dormant dans le logement = intimité maximale + zéro vol/casse/charge à gérer, pas de bouton muet à gérer).

### 6.5 LLM voix : API-first + fallback local (décision validée + comparatif coûts octobre 2026)

### 6.6 Modèle de décision : orchestrateur central + Jev TypeSafe (identifié, doc réelle lue octobre 2026)

- **Besoin** : un seul point de décision qui arbitre occupation ↔ pricing ↔ énergie ↔ ménage ↔ incidents (au lieu d'automations isolées qui se contredisent). Ex : ne pas lancer la pré-chauffe si arrivée annulée ; ne pas appliquer un prix sous plancher ; escalader bruit niveau 2 seulement si logement occupé.
- **Architecture retenue (proposition à valider ensemble)** : orchestrateur **maison 100% gratuit**, implémenté en `pyscript`/`AppDaemon` (`custom/decision-engine/`), avec :
  1. **État unifié** : `input_boolean.log1_occupation`, `input_datetime` arrivée/départ, `sensor.log1_prix_nuit`, `select.log1_llm_backend`, `binary_sensor.wan_ok`, états Versatile/ECS/Nuki/bruit/fuite/incendie, file `todo.log1_menage`.
  2. **Règles déterministes prioritaires** (sécurité > occupation > énergie > confort > prix) : incendie/fuite = tout coupe + alerte critique ; occupation = source vérité calendrier fusionné ; énergie = presets selon état ; prix = bornes plancher/plafond inviolables.
  3. **Couche jugement consultative seule** (API Mistral pour le texte voyageur + **Jev TypeSafe pour la décision structurée**, voir ci-dessous) : le modèle **propose un jugement typé** (choix/score/noul + confidence), l'orchestrateur **dispose** (valide bornes + seuils confidence + exécute). Jamais de tool-calling direct serrure/vanne/portail par un modèle.
- **OneSystem** : compris comme nom de travail de cet orchestrateur unifié (1 moteur, N logements via `logement_id`). Si OneSystem désigne autre chose (produit existant ?), à préciser avant implémentation — le plan garde l'interface stable : entrées = capteurs/calendriers/prix, sorties = scripts HA sûrs + notifications.
- **Jev = identifié : modèle System One de TypeSafe** ([introduction](https://docs.typesafe.ai/introduction), docs lues en markdown octobre 2026 — remplace l'ancienne enquête qui concluait à tort « inexistant »). Principe : on envoie un **state** (texte/JSON) + des **questions typées**, on reçoit des **réponses structurées utilisables directement en code** (pas de génération de texte à parser). 3 primitives combinables en 1 appel (évaluées en parallèle, isolées, même state) :
  - `Choice` → `{choice, probabilities, confidence}` (ex : quel service doit traiter : ménage / technique / hôte),
  - `Score` → `{score, probabilities, confidence}` (ex : niveau de frustration/bruit 0-1),
  - `Noul` → `{noul 0-1}` (ex : ce message exprime-t-il une urgence ?).
  Endpoint : `POST https://api.typesafe.ai/v1/systemone` (`Authorization: Bearer <API_KEY>`, body `{state, model: "jev-latest", questions: {...}}`, réponse `{model: "jev-1.13.0", answers: {...}, usage: {input_tokens, output_tokens}}`). SDK : `pip install typesafe-sdk` (`uv add typesafe-sdk`), `from typesafe_sdk import Choice, Noul, Score, TypeSafeClient` → `client.system_one(state, questions)`. Modèle actuel `jev-1.13.0`, alias `jev-latest` (défaut SDK) et `jev-preview`. Console/clés : `https://console.typesafe.ai/keys`, playground `https://console.typesafe.ai/playground`. Tarif : **~0,042 $/Mtok d'input, output gratuit** (≈ 0,05-0,15 €/mois pour ~1 000 décisions LCD : state ~1-2k tokens + 5-10 questions). Limites : 100K tokens/s, 80 req/s (429 → retry backoff) ; contexte 64k total (32k state + plus longue question) ; **texte seul** (pas d'image/audio/vidéo) ; **anglais prioritaire** — socle 5 + maternelle auto §5.7-ter à valider en recette en surveillant `confidence` ; pas de fine-tune (calibration via state + instructions/critères + décomposition) ; pas d'entraînement sur les requêtes (cf. Legal/DPA/ZDR).
- **Ce que Jev peut faire pour LCD** : tri urgence bruit (Noul + Score → escalade niveau 1/2/3 seulement si occupé), routage ménage interne vs prestataire (Choice + confidence), scoring no-show / surconso / risque litigation (Score composite), garde-fous des réponses Mistral (Noul « contient-il un code / une promesse hors bornes ? » → blocage), arbitrage pré-chauffe/prix avec seuils de confidence (ex : `confidence < 0,7` → revue humaine au dashboard, pas d'action auto). Patterns doc : speculative fan-out, confidence-gated routing, composite scoring, guardrails — exactement notre besoin.
- **Ce que Jev ne peut PAS faire** : générer la réponse au voyageur (rôle Mistral/LLM texte), actionner serrure/vanne/portail en direct (jamais d'effet de bord : il juge, le code HA exécute), décider seul en temps réel déterministe (toujours sous règles + bornes 75/290 € et 21 °C), remplacer astreinte/réarmement manuel/coupure physique, ni « voir » le logement sans capteurs (input = texte/state uniquement).
- **Intégration prévue** (`custom/decision-engine/` + `rest_command.typesafe_systemone` direct, clé `secrets.yaml` `typesafe_api_key:` jamais commitée, timeout 6 s, retry 1× puis règles déterministes seules si down) **ou via proxy privé (option 0 € apparent, voir ci-dessous)** : state = JSON état unifié + message/incident ; questions = 3-8 atomiques (urgence, service, gravité, confiance) ; seuils : `noul > 0,8 + confidence > 0,75` → action auto (bornée), sinon → dashboard + notif groupée. Tester FR en recette (50 requêtes/langue socle + maternelle auto §5.7-ter, comparer Groq vs Mistral vs Jev, mesurer latence/coût/confidence). **Option micro-coût** : Jev direct ~0,05-0,15 €/mois (désactivée par défaut si 0 € strict, règles déterministes + proxy Groq/Ollama suffisent) ; activable pour ~0,1 €/mois.

**6) Wi-Fi sensing humain vs animal — détection présence sans caméra/audio (expérimental, opt-in RGPD, `wifi_sensing: off` par défaut)**

> Contexte : norme **IEEE 802.11bf WLAN Sensing finalisée 2025** (Sub-7 GHz 2.4/5/6 + 60 GHz, mesures CSI/impulsion/Doppler standardisées) + routeurs Wi-Fi 7 compatibles 2025-2026 (Qualcomm Wi-Fi Sensing, Broadcom, NXP, Infineon, Origin Wireless/Cognitive Systems Aura, Xfinity/Comcast, ADT+, Plume, Linksys). Le Wi-Fi « voit » la présence via les perturbations du signal (CSI = amplitude + phase par sous-porteuse) : vide vs humain présent vs humain en mouvement vs humain statique (respiration).

**Ce que ça apporte au plan** : (a) présence même **immobile** (canapé/lit — là où le PIR est aveugle) → extinction oublis + Eco chauffage fiabilisés ; (b) **humain vs animal** : le PIR classique a une immunité animaux <25 kg, le Wi-Fi sensing vise la même chose pour éviter fausses alertes intrusion et prouver un animal non déclaré. Méthodes 2025-2026 : hauteur/zones de Fresnel (humain 1,0-1,8 m vs chien/chat 0,2-0,6 m, plusieurs antennes/liens à hauteurs différentes), allure/Doppler (humain 0,5-2 m/s micro-Doppler 20-80 Hz périodique vs trot quadrupède cadence + élevée, étalement moindre), respiration (humain 12-20/min, chien 15-30 + halètement 100-300, chat 20-30, extraite de la phase CSI en statique), durée/trajectoire (animal = passages brefs aléatoires au sol vs humain = déplacements volontaires/sédentarité). Résultats publiés : 85-95 % humain vs animal même pièce en conditions contrôlées (ESP32 + CSI 5 GHz : détection présence animale, activité bétail, rongeurs, posture chien), ~75-85 % à travers mur / multi-animaux ; startups sécu 2025 ajoutent `humain vs animal vs ventilateur/robot aspirateur` (Origin Wireless HomeBoy/Nomi, ADT + Nest WiFi sensing, Ecobee, Ring) ; usages soin personnes âgées (chute humain vs saut animal) et monitoring animalier (anxiété/aboiement corrélé mouvement, litière/cage sans wearable).

**Intégration plan (jamais seul, toujours en fusion)** : Wi-Fi sensing = 1 source parmi 4 (PIR + ouvrants + conso elec + Wi-Fi). Règle : **jamais d'action sur Wi-Fi seul** — présomption → confirmation humaine 2 sources <2 min (ex : gabarit petit/quadrupède répété + poils/photos état des lieux + ménage = faisceau de preuves animal non déclaré → frais remise en état sur justificatifs). Statique (respiration) → Eco chauffage au lieu de chauffer une pièce « vide » selon PIR. Intrusion → filtre animaux pour éviter fausse sirène (comme immunité PIR <25 kg, mais logicielle). Phase 8 : test présence immobile 30 min + test animal ami (chat/chien connu) → taux faux positifs au dashboard.

**Matériel/logiciel** : voie A achat (routeur 802.11bf / kit Origin/Aura — ~100-200 €, API sensing, 0 dev) vs voie B bricolage (ESP32 CSI 5 GHz + datasets UT-HAR/Widar3.0/MM-Fi + modèles Transformer/TinyML edge — 1-2 sem dev, ~75-85 % pièce simple). En 2026 : **voie A recommandée, `wifi_sensing: false` par défaut**, activation log1 seul après test, jamais sans opt-in.

**7) Pourquoi pas de suivi permanent — verrouillé (Wi-Fi = contrôle de cohérence, pas de géoloc permanente)**
- **Géoloc vs sensing** : la géoloc téléphone = position nominative continue d'une personne identifiée (device_tracker) ; le Wi-Fi sensing = perturbation anonyme du signal (présent/absent, silhouette, classe humain/animal) sans identité, sans audio/vidéo, sans CSI brut conservé. L'un suit QUI et OÙ en permanence, l'autre constate QUOI (occupation) ponctuellement pour une finalité listée. Seul le second est admissible en LCD, et uniquement en contrôle de cohérence croisé (jamais Wi-Fi seul).
- **4 motifs d'interdiction du permanent** : (a) **RGPD art. 5** : disproportion + minimisation — un suivi indoor continu dépasse la finalité séjour/sécurité/énergie ; consentement forcé au contrat = invalide, refus doit être sans conséquence sur le séjour ; (b) **Vie privée / pénal** : le logement loué est le domicile temporaire du voyageur (jouissance paisible, art. 226-1 Code pénal + art. 8 CEDH) — même motif que **caméras intérieures TOTALEMENT interdites depuis le 30/04/2024 même éteintes/déclarées** ; (c) **CGU plateformes** : dispositif déclaré/visible, hors chambres-SDB, pas de tracking continu — un suivi permanent = suspension d'annonce ; (d) **Chambres/SDB = zone rouge absolue** : aucun capteur de présence (PIR comme Wi-Fi) n'y est admis en suivi, même anonymisé.
- **Voyageur vs intervenant** : voyageur = occupant jouissant des lieux → opt-in ponctuel par séjour, révocable, refus sans conséquence (fallback PIR+calendrier) ; intervenant = prestataire en mission → pointage + photos avant/après sur la fenêtre d'intervention contractuelle uniquement (fiche mission signée), jamais de fond permanent hors mission.
- **Ce qui est autorisé (ponctuel)** : actif séjour/mission uniquement ; finalités listées (sécurité, énergie, respect règlement : occupants/animaux/fêtes, preuve travail) ; données = statut + classe + horodatage, jamais CSI brut/audio/vidéo/identité ; purge 90 j (interventions 12 mois pour facturation) ; info préalable annonce + règlement + affichage + QR ; double source <2 min avant toute retenue sur justificatifs via plateforme.

> « Le logement est équipé d'un système de détection de présence sans caméra ni enregistrement audio/vidéo (capteurs + signal Wi-Fi), actif uniquement pendant votre séjour et avec votre accord, aux fins de sécurité, d'économie d'énergie et de vérification du respect du règlement (occupants, animaux, fêtes). Vous pouvez refuser sans conséquence sur votre séjour. Données : présence/absence et comptage approximatif, conservées 90 jours, jamais revendues, accès hôte seul. »

### 12.2-bis Prix différencié par plateforme / logement / voyageur — légal OUI, sous 5 conditions (validé 2026-10-05)

> Réponse au doute « ce n'est pas légal » : **un prix facial différent par canal est 100 % légal SI le prix affiché est TTC tout compris AVANT résa sur chaque canal**. Ce qui est interdit, ce n'est pas de différencier — c'est d'ajouter des frais après résa, de déguiser la caution en prix, ou de discriminer selon le voyageur.

- **1) Prix facial TTC transparent par canal (L.112-1 Code conso + L.121-1 pratiques trompeuses + transparence UE)** : chaque canal affiche SON prix tout compris (nuitée + commissions répercutées + ménage/linge/taxe/personne sup./animal SI déclarés et payés via ce canal). Commissions/frais inclus dans le facial, jamais ajoutés après. Le moteur §3 applique exactement ça (`prix_canal = pivot/(1−commission) + frais_fixes`, clamp bornes).
- **2) Caution/hold ≠ prix, jamais dans le facial (§12.3)** : dépôt de garantie restitué = pas une somme acquise au loueur → exclu du prix affiché, mentionné à part (montant, mode, délai). Airbnb : caution hors plateforme INTERDITE (AirCover) ; Booking : collecte SÉPARÉE déclarée Policies ; Vrbo : caution OU Damage Protection ; direct : hold libre.
- **3) Frais annexes UNIQUEMENT si déclarés avant résa + payés via la plateforme (§12.1)** : ménage, linge, taxe de séjour (si non collectée par l'OTA), personne sup., animal — sinon exclus du facial et non exigibles. **Extras/upsells (§5.6-ter : mini-bar, late/early, kits, transfert, courses, petit-déj…) = mêmes règles : prix TTC affichés avant résa + payés via le canal, jamais exigés sur place sans pré-commande.**
- **4) Différenciation « par voyageur » = critères objectifs affichés UNIQUEMENT** : durée, nb occupants (capacité max), saison, early-bird, last-minute, jour semaine. **Jamais** selon origine, nom, photo, statut, handicap, âge, religion, orientation (art. 225-1 Code pénal = discrimination + bannissement CGU art. 2898). Une remise fidélité/direct est légale si c'est un tarif public affiché (ex « −10 % 7 nuits+ » dans l'annonce), pas un profilage.
- **5) Parité tarifaire : à vérifier contrat par contrat** : les clauses de parité LARGE Airbnb/Booking (interdiction d'être moins cher ailleurs) ont été supprimées suites aux interventions concurrence UE/FR — mais des clauses de parité ÉTROITE ou des engagements commission/visibilité peuvent subsister selon votre contrat Extranet. **Action** : vérifier Extranet Booking + CGU hôte Airbnb avant d'afficher un direct moins cher ; en pratique le direct moins cher que l'OTA (marge commission économisée) est aujourd'hui couramment admis, mais gardez la preuve contractuelle au dossier `docs/logN/contrats-ota/`.
- **Direct moteur direct (§4-bis) = liberté totale** : vos CGV fixent le pivot sans contrainte OTA (dans la limite du droit FR : TTC, L.221-28, médiation L.612-1).

### 12.6 Fiscalité LMNP, coûts par logement, parc multi-logements même propriétaire — gestion la plus autonome possible (LLM + Jev)

> Document de travail — informatif, pas un avis fiscal. À valider avec un comptable avant toute option (micro vs réel, classement, amortissements).

**12.6.1 Statut et régimes (France, meublé touristique, 1 SIREN LMNP = N logements)**

- **Immatriculation** : 1 seul SIREN LMNP au Guichet des formalités (INPI/INSEE) pour toute la personne, puis 1 SIRET par logement (même SIREN, NIC différent). Revenus = **BIC** (pas foncier). CFE due par commune d'activité.
- **Micro-BIC (défaut, zéro compta)** : abattement forfaitaire, aucun amortissement, aucune charge déduite.
  - **Non classé (loi Le Meur 19/11/2024)** : abattement **30 % dans la limite de 15 000 € de CA annuel** (au-delà → bascule réel obligatoire).
  - **Classé 1-5* Atout France (ou chambre d'hôtes)** : abattement **50 % dans la limite de 77 700 € de CA annuel**.
  - Les plafonds s'apprécient en **cumulé sur tous les logements du même foyer fiscal** — d'où le suivi parc §12.6.4.
- **Réel (option, comptable obligatoire)** : charges réelles + **amortissements** (bien hors terrain, meubles, travaux, frais d'acquisition) déduits année par année ; souvent gagnant dès que charges + amortissements > abattement micro, ou CA > plafonds. Déficit reportable (pas imputable sur revenu global en LMNP, report sur BIC futurs).
- **Classement Atout France 1-5*** : visite Office de Tourisme (~5 ans), non obligatoire mais double levier — (a) fiscal : 30 %/15 000 € → 50 %/77 700 € en micro ; (b) commercial : badge confiance + filtre plateformes. Coût visite ~quelques centaines d'€, à intégrer au CAPEX log1 si visé.
- **TVA** : exonérée par défaut en LCD pure (pas de services para-hôteliers) ; si ≥3 services para-hôteliers sur 4 (petit-déj, linge, ménage régulier, réception) → assujettissement possible → à trancher avec comptable, jamais auto.
- **Taxe de séjour** : rappel §12.5 — OTA collectent et reversent, direct (§4-bis) = vous collectez/déclarez ; **jamais de double reversement**.

**12.6.3 Optimisation fiscale — ce que le système fait et ne fait pas**

Le système **documente et alerte, il ne décide jamais** (bascule micro→réel, classement, amortissements = décision humaine + comptable, traçée `decision.logX.jsonl`).

1. **Simulateur micro vs réel par logement + parc** : à partir du CA réel (`ca_annee`), des charges saisies et d'amortissements estimatifs (barème comptable standard paramétrable), le dashboard calcule chaque trimestre : impôt micro simulé vs réel simulé → **recommandation à valider par le comptable** (jamais d'option auto).
2. **Alertes seuils** : 80 % puis 100 % des plafonds (15 000 € non classé / 77 700 € classé, **cumul parc**) → notif critique + proposition de RDV comptable + gel prudentiel des remises last-minute si dépassement imminent (proposition, validation humaine).
3. **Classement = levier chiffré** : le simulateur montre le gain micro 30 %→50 % pour justifier (ou non) le coût de la visite Atout France.
4. **Charges déductibles (réel) exhaustées par ingestion auto** : factures hardware §2, ménage/presta, commissions OTA, assurances §12.4, taxe/CFE, énergie, abonnements → OCR + catégorisation LLM (EU-only si `llm_eu_only`) → écritures pré-remplies export comptable (CSV/FEC simplifié), comptable valide.
5. **120 j résidence principale** : compteur `nuitees_principale` auto (calendrier) → blocage stop-sell au-delà (proposition validée une fois, puis auto), traçé.

**12.6.4 Parc d'une même personne — 1 SIREN, N logements, supervision agrégée**

- **Rattachement** : `fiscalite_parc.siret_siren` unique + `logN.fiscalite` par logement (régime, classement, CA, nuitées). Ajouter log3 = copier bloc + wizard §1.6.4.

- **Mutualisation** : 1 central, 1 proxy LLM, 1 UI, 1 contrat comptable, 1 PNO/cadre d'assurance multi-biens si l'assureur le permet (devis à comparer vs 1 police/logement).
- **Clôture annuelle assistée** : dossier `docs/parc/<annee>/` généré auto (CA/logement, charges catégorisées, amortissements estimatifs, taxe séjour reversée, registre nuitées) → envoi comptable en 1 clic (export chiffré), relecture annuelle tracée (`fiscalite_parc.comptable.relecture_annuelle`).

**12.6.5 Automatisation maximale — pipeline compta LLM + Jev (zéro ressaisie)**

1. **Ingestion** : photo/scan/PDF facture (PWA ménage/hôte ou email dédié) → stockage `docs/logN/compta/<annee>/` + OCR locale (Tesseract, 0 €) → **catégorisation LLM** (fournisseur, TTC/HT/TVA, logement, rubrique : hardware, ménage, commission, assurance, énergie, taxe, divers) → écriture brouillon, confiance affichée ; si confiance < seuil → file de validation humaine (dashboard HÔTE, 1 tap).
2. **Rapprochement payouts** : exports CSV Airbnb/Booking/Abritel + relevé Stripe/moteur direct (§4-bis) → matching auto résa↔paiement↔commission → `ca_annee` alimenté sans saisie ; écart >2 % → alerte. **Extras (§5.6-ter)** : chaque extra payant (mini-bar, late/early, kits, transfert, courses, petit-déj, pack télétravail, conciergerie séjour…) = ligne CA propre par extra (paiement Stripe/Swikly tagué `logX_extra_<nom>`) → marge/extra calculée (prix − coût catalogue) en Vue Finances ; partenariats à commission (voiture/vélo, excursions, resto/plage, cowork) = ligne CA « commission » au reversement presta ; kit de bienvenue offert = charge rubrique « accueil » (~4 €/séjour, tickets Intermarché), jamais du CA.
3. **Jev (décision)** : `TypeSafe Choice` (choix rubrique), `Score` (confiance, seuil validation humaine), `Noul` (anomalies : doublon, montant aberrant, TVA incohérente) — micro-coût (~0,05-0,15 €/mois §2.7), kill-switch `jev_enabled`, `cache_ttl: 0` verrouillé.
4. **Clôture mensuelle auto** : le 5 de chaque mois → récap/logement (CA, charges, énergie kWh/€, net) + récap parc + push notif + archive PDF signée horodatée.
5. **Dashboard HÔTE — onglet Finances (7e onglet, §1.6.1)** : CA/mois/logement + parc, charges par rubrique, simulateur micro/réel, jauges plafonds 15 000/77 700 €, compteurs 120 j, file validation factures, export comptable 1-clic. **Si `compta_auto: off`** : onglet réduit à saisie manuelle CA/charges (mêmes jauges, sans ingestion).
6. **Garde-fous** : `compta_auto` on/off par logement (§1.5.1) ; pièces conservées 10 ans (délai fiscal) chiffrées hors site avec backups §1.6.4 ; **clés API et exports bancaires dans `secrets.yaml`, jamais commités** ; données compta exclues du partage marque blanche (1 dossier privé chiffré/client §1.5.4).

**12.6.6 Pilotage : Vue Finances KPI, rapprochement bancaire, maintenance préventive, score ménage, registre incidents (validé 2026-10-05)**

1. **Vue Finances KPI** : RevPAR (€/nuit dispo = CA hébergement ÷ nuits dispo), prix moyen/nuit, taux occupation %, marge nette/séjour (CA − ménage − linge − énergie mesurée − commissions − accueil), CA extras/séjour, coût/séjour — par logement + parc, courbes 12 mois glissants, comparatif N-1.
2. **Rapprochement bancaire auto** : import CSV banque 1×/mois (format paramétrable) → matching payouts/compta → écart >2 % ou ligne orpheline >7 j → alerte + file validation (jamais d'écriture auto en compta).
3. **Maintenance préventive calendaire** : filtre hotte 6 mois, détartrage LV/LL 6 mois, révision clim 1 an, joints SDB 1 an, piles serrure 8 mois, contrôle DAAF mensuel, VMC 1 an → todos auto dashboard Ménage/Hôte + preuve photo clôture.
4. **Score qualité ménage** : note 1-5 + temps pointé vs ~3h attendues par rotation → moyenne/presta, alerte si <3,5 ou écart temps >20 % répété → comparatif §12.4-bis.
5. **Registre incidents + post-mortem** : tout incident critique (fuite, feu, conflit, serrure HS, double-résa) → fiche `{date, cause, impact, action, prévention}` + post-mortem 5 lignes si récidive → capitalisation multi-logements.

## 13. Conciergerie propriétaires — gestion pour tiers (2ᵉ métier, validé 2026-10-05)

Le pipeline ci-dessus devient un produit : superviser des logements tiers avec la même stack (1 HA/site + central mutualisé, marque blanche §1.5.4).

**Formules** : **Essentiel ~15 % du CA** (calendrier multi-plateformes + pricing §3 + messages + ménage + linge) ; **Sérénité ~20-25 %** (Essentiel + maintenance préventive + inventaire §5.6-bis + sinistres §12.4-bis + compta §12.6 + taxe/Cerfa) ; **Premium / intégrale ~30 % + extras** (Sérénité + déco + shooting + optimisation annonce + conciergerie voyageurs §5.6-ter + gestion travaux/copro/AG). **À la carte** : mise en valeur + shooting 150-300 €, création annonce + pricing forfait 150 €, remise en route après dégât (forfait + presta), gestion copro/syndic 30 €/mois.
**Garde-fous** : mandat écrit de gestion saisonnière par propriétaire, RC pro conciergerie, fonds via Stripe/Swikly tagué par logement (jamais de compte commun), transport/garde d'enfants = prestas assurés uniquement, données compta 1 dossier privé chiffré/client (jamais mutualisées, §1.5.4).
**Technique** : ajouter un logement tiers = copier bloc logN + wizard §1.6.4 (copro vérifiée exigée avant mise en ligne) ; supervision agrégée au central, dashboards filtrés par logement ; facturation gestion = ligne CA « gestion » par logement tiers en Vue Finances. **Comptes 5 rôles (§1.6)** : à la signature mandat → entrée `custom/acces.yaml` (`role: proprietaire`, `sous_role: proprio_logement|parc`, périmètre = ses logX) + invitation `/hote` scopée ; `gestionnaire` = périmètre logX opérés ; `prestataires` = missions §12.4-bis ; `voyageur` = PWA séjour ; `super_admin/admin` = vous seuls multi-clients.

## 14. Runbook jour J — 2 pages (accueil, rotation, incident, départ)
